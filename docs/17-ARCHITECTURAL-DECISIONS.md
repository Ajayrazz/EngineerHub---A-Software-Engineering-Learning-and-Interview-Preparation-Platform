# 17 — Architectural Decision Records

Format: Context → Decision → Alternatives → Consequences. Status: `Proposed` until user approval.

## ADR-001 Modular monolith first — *Proposed*
**Decision:** Single Spring Boot deployable with Modulith-verified modules; judge, AI, web separate. **Alternatives:** microservices day one (operational burden, premature); plain layered monolith (boundary erosion). **Consequences:** simpler ops/transactions; discipline needed; extraction path via events.

## ADR-002 Keycloak for identity, Next.js BFF holds tokens — *Proposed*
**Alternatives:** Spring Authorization Server; Auth0/Cognito (SaaS, cost/lock-in); tokens in browser (XSS risk). **Consequences:** strong security posture, extra service to run; BFF adds a hop.

## ADR-003 PostgreSQL as single source of truth, schema-per-module — *Proposed*
**Alternatives:** polyglot early (Mongo, ES). **Consequences:** FTS/pgvector reduce infra; revisit OpenSearch when FTS insufficient.

## ADR-004 Transactional outbox + RabbitMQ with idempotent consumers — *Proposed*
**Alternatives:** direct publish after commit (dual-write loss), Kafka (heavier; not needed yet). **Consequences:** at-least-once semantic; requires idempotency everywhere.

## ADR-005 Judge: custom worker on `isolate` in a no-egress VM; Judge0 rejected — *Accepted (2026-11-23)*
**Context:** must be free, secure, maintainable, Spring-integrable; Java/Python/C++ stdin/stdout first. **Decision:** thin custom worker over `isolate` (namespaces+cgroups v2) on dedicated no-egress VMs, behind a swappable `Sandbox` interface. **Alternatives:** Judge0 CE (duplicates our queue/state/test-data model, extra Ruby stack, cgroup/privilege constraints, CVE-cadence dependency), nsjail (viable equal), Piston, Docker-only (rejected), Fargate per run (slow/costly), Firecracker/gVisor (later hardening). **Consequences:** ~2–3 weeks more build effort than Judge0; full control of hidden tests, drivers, checkers; Linux-only dev needs a VM; compute cost for worker VMs; shared-kernel risk mitigated by no-egress/disposable hosts and later gVisor/Firecracker. Details: doc 10 §1. Spike in Phase 4a may revise if assumptions about isolate/cgroup v2 on the target OS fail.

## ADR-006 Premium/free are entitlement states, not roles — *Proposed*
**Context:** brief lists `PREMIUM_USER`, `FREE_USER` as roles. **Decision:** derive from subscription; expose as computed authorities. **Why:** avoids drift between payment state and role assignments; expiry is automatic. **Consequence:** role table holds staff roles only.

## ADR-007 UUIDv7 ids for domain entities; bigint for append-only logs — *Accepted; generator implemented (M0.4)*
Index locality vs. UUIDv4; non-guessable public ids. **Generated in Java** (`shared.id.Ids`, ~20 lines, RFC 9562 layout, unit-tested) rather than by PostgreSQL 18's native `uuidv7()`, because services need the id before the INSERT (events, outbox, response bodies) and it keeps us independent of the DB version. No entity uses it yet (first ones arrive in Phase 1).

## ADR-018 Unified billing core: AccessPeriods fed by mode-specific adapters — *Accepted (2026-11-23)*
**Context:** owner wants monthly/annual passes **and** auto-renewing monthly/annual subscriptions. **Decision:** every successful payment (order or subscription charge) is handled by one `PaymentCapturedHandler` that appends an immutable `AccessPeriod`; entitlements derive only from periods; `RenewalPolicy` strategies and Razorpay adapters hold all mode-specific logic. **Alternatives:** separate flows per mode (duplicated logic, divergent bugs); storing a mutable `expires_at` on user (loses history, hard to refund/audit). **Consequences:** refunds/revocation/overlap rules are uniform; small extra table; recurring can ship after passes without redesign. Pending: P-1…P-8 (doc 21 §11). Supersedes the earlier "fixed-term first" recommendation in ADR-014.

## ADR-023 Dev-stack component substitutions — *Accepted (2026-11-23)*
**MailHog → Mailpit** (MailHog unmaintained). **MinIO → RustFS** for the local S3-compatible store: MinIO no longer provides community container images (verified: pulls unavailable), RustFS is Apache-2.0 and actively developed. **Consequence:** RustFS is young; the app must use only standard S3 operations behind the `ObjectStorage` interface (ADR-019) so Garage/SeaweedFS/cloud S3 can replace it; presigned URLs to be verified when first used. ## ADR-024 CI & security tooling choices — *Accepted (2026-11-23)*
**Decisions:** (1) **Contract-first API gate:** a test compares the generated OpenAPI spec with the committed `openapi/engineerhub-v1.yaml`; the TS client is generated from it and a second check fails on drift. (2) **Scanners run as pinned CLI/containers, not marketplace actions** (gitleaks, OSV-Scanner, actionlint); third-party actions are pinned to commit SHAs. (3) **SCA = OSV-Scanner on a CycloneDX SBOM + npm lockfile**: scanning `pom.xml` alone silently skipped Boot-managed dependencies. (4) **Trivy deferred** (doc 09 originally named it): there are no Dockerfiles/images to scan yet, and I recall reports of a supply-chain compromise of Trivy's GitHub Action — I could not verify details here, so re-evaluate (and verify release integrity) when container images exist. (5) **Local git hook** (`make hooks`) instead of the Python `pre-commit` framework — no extra tool for a solo developer. (6) API docs/Swagger UI are **off by default** and only enabled in the `local` profile. **Alternatives:** OWASP Dependency-Check (needs NVD key, slow), Snyk (paid tiers), pre-commit framework. **Consequence:** GitHub-side behaviour (workflows, Dependabot, CodeQL, branch protection) is unverified until a repository exists.

## ADR-025 Method security as the single enforcement point; permissive URL layer guarded by a build-time rule — *Accepted (2026-11-23, M0.4)*
**Context:** public endpoints (course catalogue, health) must coexist with protected ones. **Decision:** the filter chain authenticates (stateless JWT) but authorizes nothing at URL level (`anyRequest().permitAll()`); every handler method must carry `@PreAuthorize` or `@PermitAll`, enforced by `EndpointPolicyArchTest` (with a negative control proving the rule can fail). Anonymous calls to protected methods → 401, wrong role → 403, both problem+json. **Alternatives:** URL-pattern allowlists in the security config (duplicated, drifts from controllers); `anyRequest().authenticated()` plus a public-path list (same drift). **Consequences:** one place to reason about access; the safety net is a CI test — a developer who bypasses CI could ship an open endpoint, so the test must stay mandatory. CSRF is disabled because the API only accepts bearer tokens and keeps no session (browser CSRF defences live in the BFF).

## ADR-026 Identity-provider outage is a 503, not a 500/401 — *Accepted (2026-11-23, M0.4)*
Found by an integration test: with Keycloak unreachable, token validation threw an unhandled exception (500, non-problem body). `ResilientJwtDecoder` maps decoder-initialisation and JWKS-retrieval failures to `IdentityProviderUnavailableException` → `503` problem+json with `Retry-After: 5`; genuinely invalid tokens stay 401. The decoder is lazy, so the API boots while Keycloak is down (public endpoints keep working) and recovers by itself (verified live).

## ADR-027 Structured JSON logs with correlation ids — *Accepted (2026-11-23, M0.4)*
Spring Boot's built-in ECS structured logging (no extra library) is the default; the `local` profile uses readable text. `CorrelationIdFilter` (highest precedence) accepts an inbound `X-Correlation-Id` only if it matches `[A-Za-z0-9._-]{8,64}`, otherwise generates a UUIDv7, puts it in the MDC, echoes it in the response header and in every problem+json. **Known risk:** unexpected exceptions are logged with message + stack trace; code must never put secrets/PII in exception messages (log scrubbing is future work).

## ADR-028 Cache Components OFF; per-request CSP nonce on dynamically rendered pages — *Accepted (2026-11-23, M0.5)*
**Context:** the Next.js 16.4 scaffold enabled `cacheComponents`/`partialPrefetching`, which prerender a static shell. A nonce-based CSP needs the nonce in the HTML, i.e. per-request rendering; prerendered HTML cannot carry it (Next docs, CSP guide). **Decision:** disable Cache Components, render every page per request (`await connection()` in the root layout) and set `Content-Security-Policy` with a fresh nonce + `strict-dynamic` in `proxy.ts` (Next 16's replacement for middleware). Production CSP has no `unsafe-inline`/`unsafe-eval` (verified: no violations in Chromium on tested pages). **Consequence / open question:** public, cacheable content pages (lessons/problems for SEO, Phase 2) cannot use per-request nonces; they will need a different strategy (hash-based CSP/SRI, or a separate route group served with a static CSP) — decide when those pages are built.

## ADR-029 BFF session design: `openid-client` + node-redis, server-side encrypted sessions — *Accepted (2026-11-23, M0.5)*
**Decision:** certified OIDC library `openid-client` v6 (discovery, PKCE S256, state/nonce, ID-token validation, refresh, RP-initiated logout); sessions in Redis: browser holds only a 256-bit opaque id in an `HttpOnly; SameSite=Lax` cookie (`__Host-` prefixed + `Secure` over HTTPS); Redis key = HMAC(id) (a key dump yields no usable cookies); value = AES-256-GCM ciphertext bound to its key via AAD (tokens unreadable from a Redis dump; values cannot be swapped between sessions); keys derived by HKDF from `SESSION_SECRET`; sliding idle timeout + absolute lifetime; new id at every login (no fixation); logout destroys the server-side session before ending the Keycloak SSO session. **Alternatives:** Auth.js v5 (beta; default JWT/cookie sessions would put tokens in the browser, DB-adapter mode adds a schema we don't need), iron-session (tokens inside the cookie), hand-rolled OAuth with `oauth4webapi` (more code to get wrong). **Consequences:** Redis is now a hard dependency of login (its outage = users cannot be authenticated; sessions are not in Postgres); rotating `SESSION_SECRET` logs everyone out (no key-rotation scheme yet).

## ADR-030 Token refresh, CSRF and proxy rules — *Accepted (2026-11-23, M0.5)*
(1) **Refresh is serialised per session** with a Redis lock because Keycloak rotates refresh tokens and treats re-use as theft: concurrent refreshes would revoke the session (tested: 8 parallel requests, 2 rounds). (2) **Only a definitive IdP refusal (`invalid_grant`, `invalid_client`, `unauthorized_client`) ends a session**; network errors/5xx keep it and yield `503 + Retry-After` (found in review: the first version destroyed sessions on any failure, which would have logged everyone out during a Keycloak outage). (3) **CSRF for unsafe BFF requests = `Origin` must equal our origin AND per-session token (`X-CSRF-Token`/form field)**, on top of SameSite=Lax; logout is POST-only. (4) **Proxy** forwards only `/api/v1/<validated path>`, allowlists request/response headers (never cookies/Set-Cookie/WWW-Authenticate), caps bodies at 1 MiB, refuses redirects, sets `Authorization` itself, and ignores any client-supplied one. (5) Login CSRF defence: the `state` is also stored in a short-lived HttpOnly cookie that must match.

## ADR-031 Transactional outbox with a JDBC relay (SKIP LOCKED + publisher confirms) — *Accepted (2026-11-23, M0.6)*
**Decision:** modules emit events only through `OutboxPublisher` (propagation `MANDATORY`: it fails outside a transaction), which appends to `shared.outbox` in the caller's transaction. `OutboxRelay` polls oldest-first with `SELECT … FOR UPDATE SKIP LOCKED`, publishes each event with **publisher confirms** (persistent messages, `eventId` = AMQP `messageId`), and marks it published in the same transaction; failures are recorded (`attempts`, sanitized `last_error`) and the relay backs off exponentially (poll × 2ⁿ, max 30 s) instead of hammering a dead broker. **Guarantees:** no event is lost once its business transaction committed; delivery is **at-least-once** (a crash after the broker confirmed but before the relay's commit republishes — proven by a fault-injection test), so consumers must be idempotent. **Ordering is best-effort only** (concurrent commits, several relays). Safe to run in several processes. **Alternatives considered:** publishing after commit (dual-write loss), Debezium/CDC (extra infrastructure), Kafka (heavier, not needed), **Spring Modulith's event externalization/publication registry** — we already use Modulith and it can externalize to AMQP; I did *not* evaluate it in depth. Chosen: an explicit table matching `docs/06`, SKIP LOCKED multi-relay, confirm handling, backoff and the idempotency ledger under our control. Re-evaluate if the maintenance burden grows. **Consequences:** one more table and a polling latency (~poll interval, default 500 ms); published rows are purged after 7 days.

## ADR-032 Consumer reliability policy: idempotent handler, quorum queues, bounded retries, DLQ — *Accepted (2026-11-23, M0.6)*
Every consumer goes through `IdempotentEventHandler`: the idempotency-ledger row and the handler's database changes commit or roll back together → exactly-once *effect* on at-least-once delivery. Queues are **durable quorum queues** (RabbitMQ 4 recommendation) owned by the consuming module and declared at start-up via `MessagingTopology.consumerQueue(...)` (a topic exchange silently drops messages that match no queue), each with a `<queue>.dlq` behind the dead-letter exchange. Handler failures are retried 3 times in total with backoff (0.5 s ×2), then dead-lettered; **malformed messages skip retries** and are dead-lettered immediately. Unroutable events are reported by the broker (mandatory + returns), logged and counted, never silently ignored. The application refuses to start without explicit broker host/credentials, never accepts `guest`, and allows plain TCP only to localhost. **Pitfall recorded:** Boot 4 renamed the listener retry property (`max-attempts` → `max-retries`, counted *after* the first attempt); the old name was silently ignored and gave 4 attempts — `MessagingConfigurationIT` now asserts the *resolved* values. **Limits:** retries run in-memory on the consumer thread (a slow message delays the queue behind it); no DLQ replay tool yet (manual procedure in docs/18).

## ADR-025 amendment (M1.1): anonymous state-changing requests are rejected at the filter chain — *Accepted (2026-11-23)*
Found by a test: with method security alone, an **anonymous** `PUT /me/preferences` returned `400` (body validation) instead of `401`, because Spring binds and validates arguments *before* the `@PreAuthorize` check. All anonymous POST/PUT/PATCH/DELETE are now refused with 401 in the filter chain (`AnonymousMutationMatcher`) before routing/binding — which also stops anonymous callers probing which routes exist. Rare public mutations (payment webhook, newsletter subscribe) must be listed in `engineerhub.security.public-mutation-paths`. GETs are unchanged (method security remains the policy point, enforced by the ArchUnit rule).

## ADR-033 Identity: just-in-time provisioning, status guard, no user id in any URL — *Accepted (2026-11-23, M1.1)*
Local users (`identity.users`, `identity.user_profiles`) are created from the verified token claims on the first authenticated call (the BFF triggers it at login via `/me`) with one atomic upsert on the unique Keycloak `sub` (`ON CONFLICT … DO UPDATE … WHERE <changed>` + `xmax = 0` to detect creation; unchanged rows are rewritten at most every 5 minutes). Creation emits `identity.user.registered` through the outbox (ids/username only, no PII). `/me` endpoints always use the principal — there is no user id in any path or body, so no IDOR surface; DTOs contain only editable fields (mass assignment impossible). User links are https-only, host-allowlisted for GitHub/LinkedIn, no user-info/ports/control characters (they will be rendered as `<a href>`). **Suspension:** an `AuthenticatedRequestGuard` SPI (shared kernel) lets the identity module veto *every* authenticated request (403 `ACCOUNT_SUSPENDED`) with a 30 s Caffeine status cache (a second instance can serve a stale "active" for ≤ 30 s). Caffeine added (Boot-managed). **Not done:** Keycloak is not told about a suspension (the user can still log in there; the API refuses them); account deletion/export flows.

## ADR-034 Authorization model: role→permission catalog + scoped grants, evaluated by one `authz` bean — *Accepted (2026-11-23, M1.2)*
Keycloak realm roles stay the *staff roles*; what a role may do lives in the database (`identity.permissions`, `role_permissions`, seeded from the docs/08 matrix by Flyway V4). A role permission is either **global** or **scoped**; scoped permissions (INSTRUCTOR, PROBLEM_SETTER) apply only to resources the user was explicitly granted (`scoped_grants`: user, permission, resource type/id, grantor, optional expiry). A grant can never exceed the role (a grant left over after a role change, or on a role-less user, is inert), expired/suspended-user grants stop working, and only permissions flagged `grantable` can be granted per resource. Endpoints ask one question — `@PreAuthorize("@authz.can('user.read')")` / `@authz.can('course.edit','course',#id)` — deny-by-default, fail-closed (errors, unknown codes, anonymous → false). **Anti-escalation:** nobody can grant a permission they do not hold globally. `AuthorizationMatrixIT` checks every role × permission cell (15 × 6) and a test fails the build if a `@PreAuthorize` references a permission code that does not exist (typo guard). **Not done:** assigning *roles* (that needs the Keycloak Admin API — scheduled in M1.5; until then roles are managed in the Keycloak console); an ADMIN cannot yet be prevented from suspending a SUPER_ADMIN (target roles live in Keycloak). Authenticated-but-unauthorized callers with a malformed body get `400` before `403` (Spring binds before method security) — low impact, noted.

## ADR-035 Audit log: append-only, hash-chained, written in the audited transaction — *Accepted (2026-11-23, M1.3)*
`admin.audit_logs` entries are inserted **inside the transaction of the audited change** (`AuditLog.record` is `MANDATORY`): an entry exists iff the action committed (tested). UPDATE/DELETE/TRUNCATE are rejected by triggers; every row carries `hash = SHA-256(prev_hash ‖ canonical fields)` (appends serialised by a transaction-scoped advisory lock), and `AuditVerifier` recomputes the chain — modification and mid-chain deletion are detected (tested inside rolled-back transactions). Captured: actor (sub, local id, roles), action, resource, before/after (only changed fields, sorted-key JSON text so hashes are reproducible), reason, correlation id, remote address, `X-Forwarded-For`/User-Agent (clipped; the HTTP firewall already rejects control characters). No PII/secrets in entries (tested). Read access: `GET /api/v1/admin/audit-logs` (+ `/verify`) with permission `audit.read`. **Limits:** the application DB user owns the table, so a DB superuser could drop the triggers (a low-privilege runtime role is a hosting-phase TODO); the chain proves *internal consistency*, not that the whole tail was not truncated (external anchoring of the head hash is future work); `X-Forwarded-For` is recorded raw and not trusted.

## ADR-036 Rate limiting and request-size limits: Redis fixed window, fail-open, per-principal — *Accepted (2026-11-23, M1.4)*
**API:** `RateLimitFilter` runs after authentication; key = JWT subject, else client address; classes read / write / admin (defaults 300 / 60 / 120 per minute, `engineerhub.limits.rate.*`). Counting is one atomic Lua call (INCR + EXPIRE on first use) on the shared Redis, so limits hold across instances. Over the limit: `429` problem+json (`RATE_LIMITED`) with `Retry-After` and `X-RateLimit-*`. **Fails open** on Redis errors (counted in `eh.ratelimit.errors`, logged): the limiter defends against abuse and must not become an outage cause; Keycloak's own brute-force detection covers credential guessing. `/actuator/*` is exempt. Trade-off: a fixed window permits up to 2x the limit across a boundary; acceptable for abuse protection, not for billing metering. New dependency: `spring-boot-starter-data-redis` (same Redis already used by the BFF). **Size:** `RequestSizeLimitFilter` (first in chain) rejects a declared `Content-Length` over 1 MiB with `413` before any parsing and counts undeclared/chunked bodies while streaming. **BFF:** `/auth/login` (20/min) and `/auth/callback` (30/min) are limited per client address; X-Forwarded-For is trusted only when `TRUST_PROXY_HEADERS=true` (right-most entry), otherwise all anonymous callers share one bucket with a 30x ceiling (a per-client limit on a shared bucket would throttle every user at once — found when the E2E suite tripped it); coarse, flood-only, but it cannot be spoofed. `/api/proxy` is already covered by the API's per-user limits. **Open:** the real client address behind the production proxy depends on the hosting decision.

## ADR-037 Keycloak realm as code: prod-safe base + dev overlay; TOTP for every staff role — *Accepted (2026-11-23, M1.5)*
**Realm split:** `infra/keycloak/base/realm.json` holds only what every environment needs (env-placeholder redirect URIs/SMTP/secrets, roles, flows, the BFF client, the role-management service account). Fake users, scripted-login clients (`engineerhub-dev-cli`, `engineerhub-dev-noaud`), a no-OTP direct-grant flow for them, the Mailpit SMTP and a wider OTP look-ahead live in `infra/keycloak/dev/overlay.json`. `scripts/build-realm.py` merges them into the gitignored `infra/keycloak/build/dev/` that compose mounts; `make realm-check` (part of `make verify`) fails if the base gains people, dev clients, localhost/wildcard redirects, literal secrets, password/implicit flows, a service account with more than `view-users`/`manage-users`/`view-realm`, a staff role without the MFA marker, or a browser flow without a required OTP step (each rule was mutation-tested). **Staff MFA:** every staff role is a composite that includes the marker role `STAFF_MFA`; the realm's browser flow `browser-staff-mfa` runs a *conditional* OTP sub-flow gated on that marker, so staff must use TOTP (first login enrols one) while learners are never prompted. The marker is ignored by the API's role allowlist. **Why all six staff roles, not only admins:** problem setters/content managers/moderators/instructors can publish content or act on users; one policy is simpler to reason about. **Consequences / honest limits:** Keycloak rejects replayed codes (proved by a test); lost authenticators need an admin reset in the Keycloak console (no recovery-code flow yet); the direct-grant (password) flow bypasses browser MFA, which is why it is disabled in the base realm and exists only for dev clients; WebAuthn/step-up (`acr`) is future work. Realm changes are applied by import only to a *new* realm: an existing dev realm must be deleted and re-imported.

## ADR-038 Staff role assignment through the Keycloak Admin API with a least-privilege service account — *Accepted (2026-11-23, M1.5)*
Staff roles are Keycloak realm roles (they are token claims), so assigning them means changing Keycloak. The API uses a dedicated confidential client `engineerhub-admin-svc` (client_credentials only; service-account user holds `view-users`, `manage-users`, `view-realm`; live-probed: clients, identity providers and client secrets return 403) through `KeycloakAdminClient` (Spring `RestClient`, 3 s/5 s timeouts, cached token, one retry on 401, upstream bodies never echoed). Keycloak 26.8 additionally requires the built-in `kc-admin-api` client scope (audience + scope) and, for realm clients, a session (`client_credentials.use_refresh_token`): both found live and encoded in the base realm. **Endpoints:** `GET/PUT /api/v1/admin/users/{id}/roles` (`user.read` / `role.grant.standard`). **Rules (all tested, three mutation-checked):** nobody changes their own roles; only a holder of `role.grant.all` (super admin) may grant or revoke `ADMIN`/`SUPER_ADMIN` or touch anyone who holds them (also applied to *suspending* an administrator, closing the earlier open item); the last `SUPER_ADMIN` cannot be removed; unknown roles are rejected; an unchanged set is a no-op without audit. **Ordering:** the Keycloak call runs *outside* the database transaction (the audit log's advisory lock must not be held across HTTP), then the audit entry + event commit in their own transaction; if that fails the change is reverted (best effort, logged loudly if the revert fails too). **Fail-closed:** without admin credentials, or when Keycloak is down, role endpoints (and an ADMIN suspending anyone) answer 503. **Effect delay:** a change reaches the user when their access token is next issued (<= 5 min; the BFF refreshes tokens). Not verified: behaviour with a production Keycloak (HTTPS, hostname config); revoking a refresh token immediately on role removal.

## ADR-039 Admin shell: server-rendered pages, 404 for non-admins, mutations through the BFF proxy — *Accepted (2026-11-23, M1.6)*
`/admin` (overview), `/admin/users` (search/filter/page), `/admin/users/[id]` (status, staff roles, scoped grants) and `/admin/audit` (filter + hash-chain verification) are Server Components that read from the API with the user's token on the server. **Gate:** every page calls `adminContext()` itself (layouts do not re-render on navigation): anonymous -> login; a signed-in user without `user.read`/`audit.read` -> `notFound()` (the area is not advertised; `forbidden()` is still experimental in this Next.js). **UI is a hint, the API is the authority:** controls are hidden/disabled from `/me/permissions` (e.g. ADMIN/SUPER_ADMIN checkboxes need `role.grant.all`), but every action is re-checked and audited by the API; refusals are shown to the user. **Mutations** are small client components calling `/api/proxy/*` with the per-session CSRF header (the browser never holds a token); a reason is required for status and role changes. All data is rendered through React's escaping (tested with an HTML reason). URL input is validated before use (UUID-only ids, clamped page numbers, whitelisted status). ## ADR-040 Catalog authoring model: live draft + published snapshot, block allowlist, scoped instructors — *Accepted (2026-11-23, M2.1)*
**Draft/publish without a second copy of the tree:** authors edit the live rows (`catalog.lessons`, `content_blocks`); *publishing* validates the lesson and writes an immutable JSON snapshot into `lessons.published_snapshot`, which is the only thing the reader API will serve (M2.2). Editing a published lesson therefore never changes what learners see until the next publish (`hasUnpublishedChanges` shows the difference); unpublishing clears the snapshot. A published lesson cannot be deleted. **Publish gate (docs/20 §3):** the publisher must confirm originality, a `content_sources` row (original / licensed / open_license / ai_assisted; licensed kinds need license + attribution; source URLs must be https) must exist, and the lesson needs at least one valid block; publishing records `reviewed_by/at`, and changing the source clears the sign-off. A course can be published only with a description and at least one published lesson. **Blocks are data, not markup:** exactly three types (`markdown`, `code`, `callout`) with a strict key allowlist, size limits (50 KB markdown, 20 KB code, 200 blocks), no control characters; markup is stored verbatim and must be rendered by a client that does not interpret HTML (M2.3/M2.4 will use a renderer with raw HTML disabled; the choice of library gets its own ADR). **Concurrency:** every edit carries `expectedVersion`; a stale version is a 409, never a silent overwrite. **Authorization:** creating/listing courses needs global `course.edit`; editing one course needs `course.edit` on that course (global for editors, a scoped grant for instructors); publish/unpublish/archive need the global, non-grantable `course.publish`, so instructors draft and content managers publish. Every lesson/section lookup is additionally scoped by the course id from the path, so a permitted course id cannot be combined with another course's lesson (404). Audited: course created/published/unpublished/archived, lesson published/unpublished/deleted, section deleted; events `catalog.lesson.published|unpublished`, `catalog.course.*`. Reordering is one transaction using deferrable unique constraints. 31 seed topics are generic CS concepts (owner may rename). **Not yet:** revision history, review workflow with a second reviewer, media assets, prerequisites, search (later milestones).

## ADR-042 CMS UI and the markdown renderer (react-markdown 10.1.0 + remark-gfm 4.0.1) — *Accepted (2026-11-23, M2.3)*

## ADR-046 Validation harness: author programs, run records, executor port, one trust boundary — *Accepted (2026-11-23, M3.3)*

## ADR-048 Learner activity statistics from events: first-completion semantics, user-timezone days, streaks — *Accepted (2026-11-23, M5.1)*

## ADR-050 One-time pass purchases with Razorpay (test mode): server-priced orders, webhook as the only grant — *Accepted (2026-11-24, M6.2)*
**Flow:** `GET /billing/quote` (final tax-inclusive amount, decided by the server) -> `POST /billing/purchases` (login; body is only `planPriceId`, optional `Idempotency-Key`) creates a **purchase intent** that snapshots price, currency, mode and period, then the provider order (`POST /v1/orders`, amount in minor units, receipt <= 40 chars, only an intent id as note: no personal data) -> browser opens Razorpay Checkout with the returned public key and order -> `POST /billing/purchases/{id}/confirm` verifies the browser callback signature (`HMAC-SHA256(order_id|payment_id, key_secret)`, checked against the order id *we stored*, so a valid signature of another order cannot be replayed) **but never grants access** -> the UI polls `GET /billing/purchases/{id}` until the server reports a final status. **Access is granted only by `PaymentCapturedHandler`** after a verified webhook (`POST /webhooks/razorpay`, `HMAC-SHA256(raw body, webhook_secret)` over the exact bytes, constant-time compare; invalid or missing signature = 401, nothing stored): it finds the intent by provider order, ignores an already recorded payment, validates amount and currency against the intent snapshot (a mismatch marks `needs_review` and grants nothing), records the payment, appends an immutable `payment` access period and emits `billing.payment.succeeded` / `billing.access.granted`. `payment.captured` and `order.paid` both lead there; a failed attempt followed by a successful payment on the same order still grants; a late `payment.failed` never undoes a paid intent. **Idempotency at four levels:** unique intent per (user, Idempotency-Key), unique provider order, unique `(provider, payment ref)` with `ON CONFLICT DO NOTHING`, the unique period per payment, plus webhook event storage keyed by the event id header (fallback: SHA-256 of the body) processed in the same transaction. **Overlap rule (P-1, proposed default, awaiting your confirmation):** a pass bought while another runs starts when the latest running period ends; month/year are calendar months/years in UTC. **Guards:** test mode only (`RAZORPAY_MODE` must be `test` and keys must be `rzp_test_...`; a live mode or key is refused at startup), blank credentials = payments off (`/billing/config`, quote not purchasable, start answers 503, webhook answers 503 so the provider retries), 20 purchase attempts per user and hour, provider calls have 3 s/8 s timeouts and are made outside database transactions, provider errors are never echoed. **Webhook endpoint** is the one anonymous state-changing path (`engineerhub.security.public-mutation-paths`, ADR-025 amendment): it authenticates by signature, not by login. **Frontend:** `/pricing` shows a TEST MODE banner and a Buy button only when payments are configured; the button shows the server's final amount before any payment; success is declared only when the server says `paid`. The CSP (now a pure, unit-tested builder) admits Razorpay origins for frames, connections and images **only on `/pricing`**, never for scripts directly (the checkout script is loaded by our nonce'd code under `strict-dynamic`); other pages get `frame-src 'none'`. **Verified:** Razorpay documentation for the Orders API, the checkout signature construction and the raw-body webhook signature (and its at-least-once, unordered delivery); signature code against independently computed HMAC vectors; the whole server side through integration tests that sign webhooks exactly as Razorpay does. **NOT verified (needs your Razorpay test keys):** a real order creation against api.razorpay.com, the real Checkout window and its CSP origin list (not published by Razorpay: confirm with the browser console), the real webhook payload field details beyond what the docs showed (`payment.entity` id/order_id/amount/currency/status are used), and the `X-Razorpay-Event-Id` header (not found in official docs; the code falls back to a body hash). **Not built:** recurring subscriptions (M6.4), billing page with renewal dates/payment history and expiry reminders (M6.3), tax configuration, invoices (M6.5), refunds and the review queue for `needs_review` intents (M6.6), coupons, reconciliation job, automatic expiry of stale intents, a retry queue for webhooks received while the receiver is misconfigured.

## ADR-051 Billing page and renewal reminders without a sweeper — *Accepted (2026-11-24, M6.3)*
**Decision:** `GET /me/billing` (login, `no-store`, ownership from the token) returns the learner's billing state **derived at read time**: status `ACTIVE`, `EXPIRING_SOON` (inside the renewal window), `EXPIRED` (premium access that was granted or paid for has ended) or `NONE` (never had it, or only revoked periods: a revoked period is not "expired access"), the date access is valid through, whole days remaining (rounded up), `renewalDue`, and the last 50 payments (date, plan, tax-inclusive amount, status). Provider references (order/payment ids) are never exposed. **Valid-through is the end of the contiguous chain:** a pass bought while another runs is queued to start when the current one ends (P-1 default), so the date shown, and the countdown used for reminders, is the end of the whole chain; a gap stops the chain. `/me/access` now uses the same calculation (before, it showed only the end of the running period). **Renewal window** = `engineerhub.billing.renewal-window-days` (env `BILLING_RENEWAL_WINDOW_DAYS`, default 7: a default, not an owner decision, change freely). **Reminder = in-app:** `/billing` shows a notice with a Renew link to `/pricing` when expiring or expired; it states that passes do not renew automatically. **No expiry sweeper:** entitlements already expire by themselves at read time (ADR-049) and status is derived, so a periodic job would add no correctness and a second source of truth that could drift. **No e-mail reminders yet:** the backend has no mail sender or scheduler (a mail library needs an ADR and a delivery decision: provider, sender domain, unsubscribe/consent wording, retention), and a "sent" reminder that nobody receives would be a fake feature (CLAUDE.md rule 2). When the owner decides, a scheduled job emitting an idempotent `billing.access.expiring` event consumed by a mail adapter fits the existing outbox/consumer pattern. **Tests:** 7 new integration tests (window boundary at 8/7/3 days, expired vs revoked-only vs wrong-plan, queued vs gapped periods agreeing with `/me/access`, payment history isolation/order/no provider ids, auth, no-store), 6 unit tests for the chain walk, 3 frontend unit tests, 2 Playwright flows; five mutants (boundary, contiguity, payments owner filter, rounding, revoked-in-expired) killed, one survived first (revoked case lacked an already-ended period) and was fixed with a stronger test. **Not built:** e-mail/push reminders, receipts/invoices (M6.5), cancel/renew for recurring plans (M6.4), refunds (M6.6).

## ADR-052 Auto-renewing subscriptions (Razorpay Subscriptions, test mode): every charge is a payment through the same grant path — *Accepted (2026-11-24, M6.4)*
**Flow:** `POST /billing/subscriptions` (login; body only `planPriceId`, optional `Idempotency-Key`; RECURRING prices only, and a one-time price is refused here just as a RECURRING price is refused by `/billing/purchases`) snapshots price, currency and period into a `subscriptions` row (Flyway V14), creates the provider **plan once per price** (cached in `plan_prices.provider_plan_ref`; a price is never edited, so its provider plan's fixed amount stays correct) and the provider **subscription** (10 years of cycles: 120 months or 10 years, because Razorpay needs a fixed cycle count; it ends sooner by cancellation or failure), outside any database transaction. The browser opens Checkout with the subscription id; `POST .../confirm` verifies `HMAC(payment_id|subscription_id, key_secret)` against **the subscription id we stored** (a signature valid for our id but sent with another id is refused) and **never grants access**; `GET .../{id}` reports `paid` once a verified charge exists. **Access comes only from the webhook:** `subscription.charged` (payload `subscription.entity.id` + `payment.entity` id/amount/currency/status) calls `PaymentCapturedHandler.subscriptionCharged`, which uses the very same period-appending code as passes: duplicate payment ignored, amount/currency checked against the snapshot (mismatch = `needs_review`, no access), immutable payment row, new access period starting where the previous one ends (so each renewal extends by one cycle), events `billing.payment.succeeded` / `billing.access.granted`. **A charge always becomes access**, even if the subscription was already marked cancelled (events are unordered and the customer paid). **Lifecycle events never grant and never regress** (`SubscriptionLifecycle`, guarded updates from an allowed-state list): `activated` -> active; `pending`/`halted` -> past_due (only from active); `cancelled` -> cancelled (from any live state, not from completed); `completed`; `authenticated`/`paused`/`resumed`/`updated` ignored. A late `activated` can never revive a cancelled subscription (mutant-checked). **Cancel** (`POST .../{id}/cancel`, owner only, someone else's looks missing): tells the provider `cancel_at_cycle_end` first and flips to `cancel_scheduled` only if the provider agreed (503 and unchanged otherwise, retryable); idempotent; paid access and the current period are untouched and nothing is refunded (docs/21 §7). **One live subscription per user and plan**, enforced by a partial unique index (P-1 proposed default; the yearly and monthly prices of one plan count as the same plan), freed when it ends or fails. **Billing summary:** `GET /me/billing` gains `subscription` (status, amount, period, `renewsOn` only while it will really renew); an actively auto-renewing user gets no "renew now" reminder (it renews itself), a cancel-scheduled one does. UI: Subscribe button on `/pricing` (shows the repeating amount and how to stop before paying), subscription card with a two-step "Cancel auto-renew" on `/billing`. **Decisions not taken for you:** *no grace period* (P-2): access ends at the paid-through date whatever the status; *no resume* of a cancelled subscription (buy again); *no switching/proration* (P-3): cancel, then subscribe or buy a pass; *no coupons* on recurring (P-5). **Verified:** the signature construction (independent HMAC vector, order matters), the whole server side through 20 integration tests with a provider test double (start validation, one plan per price, no personal data in provider notes, idempotency, provider failure and retry, confirm never grants, forged/duplicate/mismatched/unknown/uncaptured events, renewal chaining, out-of-order events, cancel and its failure, summary rules, ownership), 12 mutants (10 killed; one equivalent because the payments uniqueness constraint returns the same answer; two real gaps found and closed: `completed` then `cancelled`, and a valid signature with a wrong subscription id), 5 frontend unit tests, 1 Playwright flow on a database-seeded subscription. **NOT verified (needs your Razorpay TEST keys and the docs/dashboard):** the exact request bodies of `POST /plans` and `POST /subscriptions` (period `monthly`/`yearly`, interval, item, `total_count`, accepted maximum of 120 cycles), whether `cancel_at_cycle_end` takes `true` or `1` (if ignored the provider would cancel at once, which our `subscription.cancelled` handling tolerates because paid periods stay), real `subscription.*` payload fields and the `payment.status` value on `subscription.charged`, the provider's retry schedule and what `pending`/`halted` mean in practice, Checkout options for subscriptions and the CSP origins they need (same origin list as orders is assumed), and **the Indian rules for recurring card/UPI payments** (first-payment authentication, per-transaction limits, pre-debit notification duties and who sends them): until confirmed, nothing may go live and this must be checked with Razorpay and your adviser (P-4). **Not built:** grace period, resume, plan switching, e-mail notices for failed renewals (no mail infrastructure, see ADR-051), update-payment-method flow (the provider hosts it; we have no link yet), invoices/receipts (M6.5), refunds (M6.6), reconciliation against the provider (M6.7).

## ADR-053 Tax configuration, receipts and tax invoices; Apache PDFBox — *Accepted (2026-11-24, M6.5)*
**Principle:** the system decides no tax fact. Flyway V15 has a single settings row that starts `UNCONFIGURED`, no tax rule, and no seller details. **Modes:** `UNCONFIGURED` issues nothing (payments and access are unaffected); `DISABLED` issues **receipts that contain no tax wording at all** (no "tax", "GST", "SAC" or "GSTIN", tested by reading the PDF back); `ENABLED` issues **tax invoices** from owner-entered rules and seller details. **Admin API** (`billing.manage`, audited): `GET/PUT /admin/billing/tax`, `POST /admin/billing/tax/rules`, `PATCH .../rules/{id}`. Validation is shape only: GSTIN has the 15-character format (no checksum, no registration check), SAC is 4-8 digits, a rule is 0.01 %..50 % with a sane date range, active rules cannot overlap, ENABLED needs complete seller details and at least one active rule, and the last active rule cannot be switched off while ENABLED. **Math:** prices are tax-inclusive; `tax = round_half_up(total * rate / (1 + rate))` on integer minor units, `net = total - tax`, so net + tax always equals what the customer paid (database check too); property-tested against a BigDecimal reference over 100,000 random cases. The rounding rule is a documented default awaiting the accountant (P-4). **Issuing:** a document is issued inside the payment-capture transaction by the same code for passes and every subscription charge, and lazily on the owner's first download for payments captured before configuration (issue date is then later than payment date and both are printed). The payment row is locked first, so concurrent issues of one payment consume one number (tested with 8 threads); numbers are gap-free per financial year (April-March in Asia/Kolkata, a default for P-4 to confirm) and type (`RCPT/2026-27/000001`, `INV/...`), allocated from a row-locked counter in the same transaction as the insert. If ENABLED but no rule covers the payment date or seller details are incomplete, nothing is issued and access is still granted. **Immutability:** a document is a snapshot (amounts, rule name and rate, seller details, plan, customer name at issue time); a database trigger refuses UPDATE and DELETE, so later configuration changes cannot alter it (tested, including direct SQL). **Download:** `GET /me/payments/{paymentId}/document` returns the PDF (`attachment`, `no-store`) to the payment's owner only; anyone else, staff included, gets 404. The PDF is rendered on demand from the snapshot, so there is no file storage. **Library:** Apache PDFBox 3.0.8 (Apache-2.0, ASF-maintained, pure Java, built-in Helvetica so no font files) over OpenPDF (LGPL/MPL; either would do) and over HTML-to-PDF engines (they parse markup, which is an injection surface). We draw only our own text lines; every string is reduced to printable ASCII first (so the rupee sign prints as "INR", and user-chosen plan or customer text cannot break the encoding or forge a line; tested with hostile input). **Test mode:** while payments are in test mode every document states it is not a valid receipt or tax invoice. **UI:** billing page "Receipt" column (downloads through the BFF; a refusal shows a message instead of saving an error page), `/admin/billing` "Tax and documents" panel that says what is not decided. **Tests:** 5 + 5 unit (math, financial-year boundaries, PDF content and hostile text), 14 integration, 4 frontend unit, 1 Playwright flow including a real PDF download; fourteen mutants killed (one survived first: ENABLED without seller details was masked by the missing-rule check, fixed with a stronger test). **NOT decided / not built (P-4, needs your accountant):** whether to charge GST at all, rate, SAC, GSTIN rules, invoice format and numbering rules, financial-year handling, rounding, treatment of refunds; **CGST/SGST vs IGST split and the customer's state / optional GSTIN at checkout are not built, so `ENABLED` is not fit for real customers yet**; **credit notes** (they need refunds, M6.6); admin list of issued documents; e-mailing documents; the invoice PDF is plain (no logo, no QR/e-invoice IRN).

## ADR-054 Refunds: requests, review, provider processing, credit notes — *Accepted (2026-11-24, M6.6)*
**Principle:** mechanism, not policy (P-6). Flyway V16 has a refund settings row that starts with **no policy text, no request window, no approval threshold**; the owner writes them in `/admin/refunds`. Learners see the policy exactly as written (plain text, never rendered as markup), or "No refund policy has been published yet". A learner can always *ask*; a person decides every outcome. **Workflow** (docs/21 §7): `requested -> under_review -> approved -> processing -> processed`, plus `rejected` and a retryable `failed`; one open request per payment (partial unique index); every transition is a guarded update, audited, and published through the outbox. **Learner API:** `POST /billing/refund-requests` (own payment only, valid reason, owner's window, something left to refund, 10 requests a day), `GET /me/refund-requests`, public `GET /billing/refund-policy`. The decision note is shown to the learner only for rejected or processed requests. **Admin API (`billing.manage`):** settings, queue with status filter, detail with attempts and flags, `review`, `approve` (full or partial amount), `reject` (note required), `retry`. **Safety rules:** the refundable amount is the payment minus pending and processed refunds, computed under the request's row lock, so a refund can never exceed what was paid (a second concurrent approval gets 409 and the provider is called once: tested with two threads); when the owner sets an approval threshold, an amount at or above it needs a **second admin, different from whoever started the review**; the provider call happens outside any database transaction; a provider failure marks the attempt and the request `failed` and changes nothing else; **a retry requires the admin to confirm they checked the provider**, because a timeout can hide a refund that actually happened and a blind retry would pay twice (the API refuses without `confirmNotRefundedAtProvider`); a request that is processing or processed can no longer be rejected or approved again. **Finishing a refund** (`finalizeRefund`, one idempotent code path used both when the provider answers "processed" and by the signed `refund.processed` webhook; `refund.failed` marks the attempt failed): payment becomes `refunded` or `partially_refunded`; a **full** refund ends the access that payment bought (the owner can switch this off; a partial refund never ends access); cancelling a subscription and refunding are independent (a subscription payment can be refunded and the subscription keeps running); a **credit note** is issued when the payment had a receipt or tax invoice (immutable snapshot, gap-free `CN/FY/seq`, names the document it reverses, the refunded amount split by the *original* document's rate, no tax wording against a receipt; PDF download for the owner only). **Flags, not decisions:** `GET /admin/billing/refund-flags` lists payments taken twice for the same plan within a day (switchable) and payments with no access after 15 minutes, each with a suggested action; nothing is refunded or activated automatically. **UI:** "Request a refund" per payment, the owner's policy and the user's requests with their status and credit notes on `/billing`; `/admin/refunds` (queue, flags, settings) and `/admin/refunds/[id]` (review, approve, reject, retry with the provider check). **Tests:** 19 integration (policy and settings, authorization table, ownership, window, full/partial/repeated refunds, access revocation and the owner's switch, four-eyes, rejection, provider failure and checked retry, pending refund finished once by the webhook, failed and unknown refund events, concurrent approval, credit notes with and without a document, tax-invoice credit note split, immutability, subscription independence, queue, flags), 1 PDF test, 4 frontend unit, 1 Playwright flow; sixteen mutants killed (one survived first: a processed or processing request could still be rejected, fixed). **NOT verified (needs your Razorpay TEST keys):** the real `POST /payments/{id}/refund` request and response (`amount`, `notes`, status values `processed`/`pending`), the real `refund.*` webhook payload (`payload.refund.entity.id` is assumed), and whether the provider offers an idempotency key to make retries safe. **Known limits:** a refund the provider reports `pending` whose webhook is lost stays `processing` until the reconciliation job (M6.7) exists, and a webhook for a refund whose reference we stored too late is ignored as unknown; no admin credit-note download; no partial-refund wording for the policy; refunds made directly in the provider dashboard are not picked up (M6.7).

## ADR-055 Reconciliation, the Live Readiness Gate, and abandoned checkouts — *Accepted (2026-11-24, M6.7)*
**Reconciliation (docs/21 §6.7).** Flyway V17. The provider port gains `listPayments` and `listRefunds` (Razorpay `GET /payments` and `GET /refunds` with `from`, `to`, `count`, `skip`, paged to at most 2,000 items; a cut-off listing is reported as `partial` and proves nothing about absence). A **pure function** (`Reconciler.compare`) compares the provider's last 48 hours with what we recorded and returns drift: `missing_payment` (captured for one of our orders but never recorded: a lost webhook), `unknown_provider_payment`, `amount_mismatch`, `refund_amount_mismatch` (a refund made outside this system, or a lost event; an in-flight refund that explains the provider's total is not drift), `refund_stuck` (processed at the provider, still pending here for over 15 minutes), `missing_at_provider` (only for a complete listing and only well inside the window). Attempts that never carried money (created, authorized, failed) are ignored. **A run never changes a money record.** Each difference becomes a finding (one open finding per kind and provider reference, however many runs see it); an admin may **apply** the two safe fixes (record the lost payment through the same single grant path as the webhook; finish the refund the provider already processed through the one idempotent refund path) or **acknowledge** any finding with a note; both are audited. The job runs **nightly** (`engineerhub.billing.reconciliation.cron`, default 02:30; off in tests) and on demand from `/admin/reconciliation`. Only one run can be `running` (partial unique index, so a second instance or a manual click is refused with 409), a crashed run is cleaned up after an hour, an unreachable provider is an `error` run with a generic note, and unconfigured payments give `skipped`. **Abandoned checkouts** (docs/21 §10 required them and nothing existed): the same run expires purchase intents past their lifetime (`expired`; a payment that still arrives is honoured because money taken is never ignored, and a paid intent is never expired) and fails subscription checkouts untouched for 24 hours with no payment; separately, starting a subscription supersedes the same user's checkout for that plan if it has had no payment and no activity for 30 minutes (before this, one abandoned checkout blocked that user from subscribing again). **Live Readiness Gate (docs/21 §9).** Nine items exactly as the design lists them, each an attestation by a **SUPER_ADMIN** (global `settings.manage`, which only that role holds; billing managers can read), with a note, audited. The system can check three things itself, so those items cannot be ticked, and the gate cannot be opened, unless the check holds at that moment: a tax mode is chosen, a refund policy is published (Terms and Privacy are not tracked here), seller name and address are present. The gate opens only when every item is done and every check passes; un-ticking anything closes it at once; closing is always allowed. **The gate enables nothing.** This build refuses `RAZORPAY_MODE=live` and `rzp_live_` keys at startup whatever the gate records; the gate is the recorded precondition that a future, deliberate code change must check before it lifts that refusal, and lifting it also needs the real-provider verification below plus changes that are not made here (test-mode banners, document test flags, checkout config). **Contract hygiene found on the way:** two API types sharing a simple name overwrite each other in the generated OpenAPI contract (a colliding `RunView` showed up in the generated client), and four older pairs already did (`GrantRequest`, `PublishRequest`, `SourceRequest`, `SourceView`). They are renamed (`AccessGrantRequest`, `ProblemPublishRequest`, `ProblemSourceRequest`, `ProblemSourceView`; wire format unchanged) and `ApiSchemaNamesArchTest` now fails the build on any new clash. **Tests:** 8 pure comparison, 13 reconciliation integration, 6 gate integration, 2 added purchase tests (browser/webhook race, rebuy after expiry) and 1 annual subscription test to complete the matrix, 1 architecture test, 3 frontend unit, 2 Playwright; seventeen mutants killed (four needed a second pass; one exposed that the "never fail a paid checkout" clause had no test, now covered). **NOT verified (needs your Razorpay TEST keys):** the real list endpoints (field names such as `amount_refunded` and `order_id`, paging, rate limits), how subscription payments appear in the provider's list (they carry no order of ours, so a lost subscription webhook is reported as `unknown_provider_payment` and cannot be applied automatically), and the whole matrix against Razorpay's test mode. **Not built:** alerting (findings are visible only in the admin page), per-finding history, reconciliation of subscriptions as such, a multi-instance lock beyond the single running-run rule.
